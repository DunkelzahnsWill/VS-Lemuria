**G24, part 3: where features meet.** A new section under "How Lemuria counts features", in four points.
1. *The folder decides.* What lies in a feature's folders is that feature's, and that feature's brief describes it.
   Why this reading and not the other, "the brief decides": the patch gate of rule 7 tests "the folders of one
   feature" against "that feature's brief". If the duets' brief described code in the machines' folders, a fix there
   could leave the machines' brief "true as written" and break the duets', and the gate would not see it. My entry of
   04:42Z leaned on this reading (its decision 1). A diary is not the Road Bible, as G24 says, so the book now says
   it.
2. *The briefs come first.* Where a feature's work would add to or change what lies in another feature's folders, that
   feature's brief is changed first, the way a settled brief is changed, and no code goes into a feature's folders
   before that feature's own brief is settled and describes it. This answers the first of the two things G24 leaves
   open under either reading: when step 1's code changes Memory, both briefs must be settled, the duets' and the
   machines', and the machines' brief must say what is added. So the nine briefs of R3 come before any such code.
   I added that such changes "may ride in the pull request that carries the new feature's brief". Why: a new brief and
   a change to a settled brief go the same way in rule 4 (read by the review thread, merged by the owner), R3 already
   has nine briefs go "in one batch", and it saves the owner a merge for each feature.

   coordinator, at 06:18Z, and the question is on main as R23.

   Reading B: rule 2 has a brief say "which existing parts it touches", and no rule keeps a feature's PR inside its
   own folders, so the code rides in the feature's PR once the touched brief is changed.
